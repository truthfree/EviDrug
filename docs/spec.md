# 개발 기반 스펙

## 1. 문서 목적

이 문서는 EviDrug의 기능 계획에 앞서 합의한 개발 및 운영 기반을 기록한다.
구체적인 기능 범위와 에이전트 동작은 별도의 계획 문서에서 정의한다.

이 문서에는 목표 운영 원칙도 포함한다. 현재 구현·검증 여부는
[프로젝트 현황](project-status.md)과 [현재 UX](ux/current-experience.md)를 기준으로 구분한다.

## 2. 배포 원칙

- 실제 접근 가능한 운영 서비스의 배포를 프로젝트의 필수 완료 조건으로 삼는다.
- 초기 배포 대상으로 Vercel을 고려하되 최종 배포 플랫폼을 고정하지 않는다.
- 서비스 고도화에 따라 프론트엔드와 백엔드를 포함한 전체 시스템을 AWS 또는 GCP로 이전할 수 있어야 한다.
- 도메인 로직과 플랫폼별 설정을 분리하고, 설정 및 비밀정보는 환경변수로 주입한다.
- 로컬, CI 및 운영 환경의 차이를 줄일 수 있도록 Docker 빌드를 지원한다.

## 3. 기술 스택

### 프론트엔드

- React
- TypeScript
- Vite

### 백엔드

- Python
- FastAPI
- Celery: 장시간 분석 작업의 비동기 실행과 재시도 관리
- HTTP API를 통해 프론트엔드와 통신한다.

### 데이터베이스

- PostgreSQL
- SQLAlchemy 2: 애플리케이션의 데이터 접근 및 ORM
- Alembic: 데이터베이스 스키마 마이그레이션
- Psycopg 3: PostgreSQL 드라이버
- FastAPI 요청마다 독립된 SQLAlchemy `AsyncSession`을 사용한다.

### 작업 큐

- Redis: API가 등록한 작업을 worker에 전달하는 메시지 브로커
- Redis는 영속적인 분석 상태나 결과의 기준 저장소로 사용하지 않는다.
- Celery 결과 백엔드의 데이터가 아니라 PostgreSQL에 기록된 상태와 결과를 서비스의 기준 데이터로 사용한다.

## 4. Python 환경 및 의존성

- 일반적인 Python 서비스의 프로젝트 및 의존성 관리는 uv를 기본으로 한다.
- `pyproject.toml`에는 지원 Python 버전과 직접 의존성 조건을 선언한다.
- `uv.lock`에는 해결된 의존성 버전을 기록하고 Git으로 관리한다.
- 로컬 가상환경인 `.venv`는 Git으로 관리하지 않는다.
- 배포 빌드에서는 잠금 파일과 프로젝트 설정의 불일치를 허용하지 않는다.
- 설치가 복잡한 모델은 Linux Docker 환경에서 설치, 모델 로딩 및 단일 추론까지 먼저 검증한다.
- uv로 안정적인 환경을 구성할 수 없는 모델에 한해 Conda 기반의 독립 컨테이너를 허용한다.
- 하나의 컨테이너에서 uv와 Conda를 동시에 주 의존성 관리자로 사용하지 않는다.
- 서로 충돌하는 모델 의존성은 별도 컨테이너로 격리하고 각 컨테이너가 자체 잠금 명세를 갖게 한다.

## 5. 컨테이너 및 버전 관리

- Docker 이미지는 Python을 포함한 전체 실행 환경의 배포 단위로 사용한다.
- Python 버전은 프로젝트 선언과 Docker 베이스 이미지에서 일치시킨다.
- Python 패키지는 uv 또는 예외적으로 선택한 Conda 잠금 명세로 고정한다.
- 모델 가중치와 데이터셋은 버전 및 체크섬을 별도로 기록한다.
- Docker 베이스 이미지는 명시적인 버전으로 지정하고 운영 이미지에는 Git commit SHA를 연결한다.
- 특정 클라우드 서비스에 직접 결합되는 코드는 어댑터 경계 안에 둔다.

## 6. 분석 실행 구조

### API와 worker 분리

- FastAPI는 분석 요청의 접수, 입력 검증, 작업 상태 조회 및 결과 제공을 담당한다.
- 시간이 오래 걸리는 외부 API 조회와 모델 추론은 별도 worker 프로세스가 실행한다.
- API와 worker는 같은 코드 저장소와 도메인 모델을 공유하되 서로 다른 실행 명령과 Docker 컨테이너로 동작할 수 있어야 한다.
- 로컬에서는 함께 실행할 수 있지만 배포 환경에서는 독립적으로 배치하고 확장할 수 있어야 한다.
- PostgreSQL에 기록된 작업 상태와 결과를 기준 데이터로 사용하며 작업 큐는 실행 전달 수단으로 한정한다.

### 작업 전달과 데이터 경계

- FastAPI는 PostgreSQL에 분석 작업을 먼저 기록한 뒤 Celery를 통해 Redis 큐에 등록한다.
- 큐 메시지에는 큰 입력 데이터나 분석 결과를 넣지 않고 `analysis_id`와 실행에 필요한 최소 식별 정보만 전달한다.
- worker는 `analysis_id`를 사용해 PostgreSQL에서 입력과 현재 상태를 읽고, 중간 상태와 최종 결과를 PostgreSQL에 저장한다.
- Redis 데이터가 유실되더라도 PostgreSQL의 작업 기록을 통해 미완료 작업을 식별하고 복구할 수 있어야 한다.
- 동일한 작업이 한 번 이상 전달될 수 있음을 전제로, worker는 `analysis_id`를 기준으로 완료 상태를 확인하고 중복 결과 생성을 방지한다.

### 요청 및 상태 흐름

1. 프론트엔드가 FastAPI에 분석 요청을 보낸다.
2. FastAPI가 입력을 검증하고 PostgreSQL에 작업을 `queued` 상태로 저장한다.
3. FastAPI가 작업을 실행 대기열에 등록하고 작업 ID를 즉시 반환한다.
4. worker가 작업을 가져와 `running`으로 변경하고 에이전트 실행 그래프를 수행한다.
5. worker가 각 단계의 상태와 결과를 PostgreSQL에 저장한다.
6. 프론트엔드는 작업 ID를 사용해 진행 상태 API를 주기적으로 조회한다.
7. 작업이 종료 상태에 도달하면 프론트엔드는 polling을 멈추고 최종 결과 또는 실패 정보를 표시한다.

분석 작업은 최소한 `queued`, `running`, `completed`, `partial_failure`, `failed` 상태를 구분한다. 개별 에이전트 단계는 대기, 실행, 완료, 실패 및 선행 입력 부족으로 인한 건너뜀 상태를 별도로 기록한다.

### 진행 상태 조회

- 초기 구현은 프론트엔드가 FastAPI의 분석 상태 조회 API를 호출하는 HTTP polling 방식을 사용한다.
- 기본 조회 주기는 2~3초로 하며 실제 값은 프론트엔드 설정으로 관리한다.
- 상태 조회 API는 PostgreSQL을 조회하며 polling 요청이 Celery나 Redis의 실행 상태에 직접 의존하지 않게 한다.
- 응답에는 전체 작업 상태, 각 에이전트 단계의 상태, 마지막 갱신 시각 및 현재 제공 가능한 결과를 포함한다.
- `queued` 또는 `running`이면 polling을 계속하고 `completed`, `partial_failure` 또는 `failed`이면 polling을 종료한다.
- 일시적인 네트워크 오류 한 번으로 분석 실패를 표시하지 않는다. 연속 조회 실패 시 조회 간격을 점진적으로 늘리고 성공하면 기본 주기로 되돌린다.
- 페이지 재접속 시 동일 작업의 조회를 재개하는 것이 목표다. 현재 UI는 자동 복원하지 않으며,
  소유 세션에서 분석 ID로 전문 저장 결과를 수동 조회한다. 결과 조회 자체는 polling이 아니다.
- polling 부하나 더 즉각적인 단방향 갱신이 필요해지면 SSE 도입을 검토한다. 클라이언트에서 실행 제어 명령을 지속적으로 보내야 하는 요구가 생기기 전에는 WebSocket을 도입하지 않는다.

### 에이전트 실행 의존성

- Target Hypothesis는 적응증과 선택적 표적 정보를 바탕으로 질환 연관성과 소분자
  tractability를 구분한 표적 shortlist와 검증된 단백질 서열을 확정한다.
- ADMET은 SMILES만 필요하므로 Target Hypothesis와 독립적으로 시작할 수 있다.
- DTA는 Target Hypothesis가 하나 이상의 유효한 UniProt ID와 단백질 서열을 제공한 뒤에만
  시작한다. 후보별 fan-out은 DTA Agent 내부에서 공통 실행 ledger를 사용한다.
- DTA에 필요한 표적 입력이 확보되지 않으면 일반 실행 실패와 구분되는 `skipped_due_to_missing_target` 상태를 기록한다.
- Decision은 Target Hypothesis, ADMET 및 실행 가능한 DTA가 종료 상태에 도달한 뒤 사용 가능한 결과를 종합한다.
- 일부 결과가 실패하거나 누락되어도 확보된 근거로 판단할 수 있으면 `partial_failure`와 데이터 공백을 포함한 결과를 반환한다.

### 재시도 및 안정성

- Celery의 재시도 기능을 사용하되 외부 API 또는 모델 실행 재시도는 원인이 일시적이고 새로운 결과를 얻을 가능성이 있을 때만 제한된 횟수로 수행한다.
- 재시도 간격은 지수 백오프와 지터를 적용하고 최대 재시도 횟수와 최대 대기 시간을 작업 종류별로 제한한다.
- 동일 작업의 중복 실행이 데이터와 결과를 중복 생성하지 않도록 작업 ID를 기준으로 멱등성을 보장한다.
- 선행 단계의 실패를 후속 단계의 일반 오류로 변환하지 않고 의존성 누락 상태로 전파한다.
- 각 단계에서 이미 생성된 중간 결과는 후속 단계 실패 시에도 보존한다.

### 배포 경계

- 프론트엔드는 Vercel 배포를 기본으로 한다.
- 상시 대기하거나 실행 시간이 긴 Celery worker는 Vercel Functions에 두지 않고 장기 실행 프로세스를 지원하는 Docker 컨테이너 환경에 배포한다.
- FastAPI, Celery worker, PostgreSQL 및 Redis의 접속 정보는 환경변수로 주입하며 특정 클라우드의 전용 API를 도메인 로직에서 직접 사용하지 않는다.
- 초기 컨테이너 호스팅 서비스를 변경하거나 전체 시스템을 AWS 또는 GCP로 이전하더라도 애플리케이션의 작업 계약과 데이터 모델을 유지할 수 있어야 한다.

## 7. 접근 제어

### 공개 범위와 보호 범위

- 랜딩 페이지, 서비스 설명 및 별도로 선별한 사전 생성 예시는 인증 없이 공개할 수 있다.
- 새로운 분석 실행, 분석 상태 조회 및 분석 결과 조회 API는 인증된 세션에만 허용한다.
- 보호 여부는 프론트엔드 화면 표시가 아니라 FastAPI의 인증 의존성에서 일관되게 검사한다.
- 초기 버전은 개별 사용자 계정을 만들지 않고 하나의 공용 접근 코드로 제한된 사용자에게 접근 권한을 부여한다.

### 접근 코드와 세션

- 접근 코드는 HTTPS 요청 본문으로만 전송하며 URL, 브라우저 저장소 및 로그에 기록하지 않는다.
- 접근 코드의 평문을 저장소나 프론트엔드 번들에 포함하지 않는다. 서버는 비밀번호 해시만 환경변수 또는 배포 환경의 비밀정보 관리 기능으로 전달받아 검증한다.
- 인증 실패 응답은 코드의 존재 여부나 검증 세부사항을 노출하지 않으며 반복 인증 시도에는 IP 기반 요청 제한을 적용한다.
- 인증에 성공하면 서버는 기본 8시간 동안 유효한 서명된 세션 쿠키를 발급한다. 유효기간은 환경별 설정으로 조정할 수 있다.
- 세션 쿠키에는 `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` 속성을 적용하고 `Domain` 속성을 지정하지 않는다.
- 세션에는 접근 코드 자체를 넣지 않으며 만료 시각과 인증 범위 등 최소 정보만 포함한다. 쿠키 서명 비밀정보는 접근 코드와 별도로 관리한다.
- 로그아웃 시 세션 쿠키를 즉시 만료시키며 접근 코드 또는 서명 비밀정보를 교체하면 기존 세션을 무효화할 수 있어야 한다.

### API 보호

- 운영 환경에서는 프론트엔드와 API를 동일한 사이트의 하위 도메인으로 구성하고, CORS는 허용된 프론트엔드 origin과 credential 요청만 명시적으로 허용한다.
- 분석 생성 API에는 인증 제한과 별도로 IP 및 세션 기준 요청 제한을 적용해 비용 남용을 방지한다.
- 상태 및 결과 조회는 유효한 세션뿐 아니라 해당 분석을 생성한 세션의 소유권을 검사한다.
  다른 세션과 CLI replay는 웹에서 조회할 수 없다. 재인증해도 이전 세션 결과 접근은 보장하지 않는다.
- 쿠키를 사용하는 상태 변경 요청은 허용된 `Origin` 검증을 포함한 CSRF 방어를 적용한다.
- 사용자별 기록, 개별 권한 회수 또는 외부 사용자 공개가 필요해지면 인증 경계를 유지한 채 OAuth/OpenID Connect 기반 계정으로 확장한다.

## 8. 브랜치 전략

- `main`은 운영 배포 브랜치, `dev`는 공용 통합 및 스테이징 브랜치로 사용한다.
- 모든 작업 브랜치는 Issue를 기반으로 생성하고 첫 커밋으로 정해진 빈 시작 커밋을 남긴다.
- 상세한 브랜치 종류, 명명법 및 병합 흐름은 [브랜치 전략](./team-rules/branch-strategy.md)을 따른다.
